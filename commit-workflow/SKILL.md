# 分组提交工作流

在当前 Git 仓库执行用户偏好的提交流程。读取该仓库适用的规则，依据真实改动分组，不预设语言、目录名、角色名或提交数量。

## 检查改动并给出结论

1. 检查当前分支、工作区、暂存区和未跟踪文件，阅读本次范围内的实际差异，明确已有暂存内容是否属于本次任务。保留用户其他改动及暂存状态。
2. 按目的、模块职责和依赖关系组织可审阅的逻辑提交。依赖先于使用方；必须同步生效的跨模块修改保持在同一提交。不要为凑数量强行拆分。
3. 对应测试和模块 README 随实现提交；总览文档、现有任务清单及验收汇总通常最后提交。公共配置放入最相关的一组。
4. 先给出简洁的拆分结论，列明提交数量、每组内容或关键路径、拟用标题和执行顺序；说明会影响提交的实际验证结果或未解决问题。

## 确认范围

- 用户直接要求 `commit` 或“提交”时，给出拆分结论后默认连续执行暂存和提交，不再等待一次额外确认。
- 用户只要求分析、审阅、“先给结论”或明确要求确认后再提交时，本轮保持只读，等待用户确认。用户后续明确指令优先。

## 依次暂存与提交

1. 多个 Agent 共用工作树时，由当前主会话统一操作 Git；先协调当前组文件的写入，避免并发暂存和提交。
2. 每组按明确路径或补丁暂存。检查 `git diff --cached`、文件清单和 `git diff --cached --check`，确保只包含该组获准内容，不混入其他组、构建产物或本地个人配置。
3. 按实际改动和仓库要求完成相关构建、测试或文档检查。仅拆分提交且内容未变时，沿用已有有效验证结果，不机械重跑；如实记录未验证项。
4. 提交标题沿用仓库约定；无其他约定时采用 `type(scope): summary`，总览文档可用 `docs: summary`。按确认顺序逐组提交，不并发执行 Git 写操作。

## 核对并汇报

- 核对各 commit 的文件范围、顺序与剩余工作区。按仓库既有约定更新进度记录，不为此另建重复账本。
- 报告每个 commit 的短 hash 和内容、验证结果、遗留改动及推送状态。
- push 按用户明确授权执行，不从 commit 请求推断推送授权；已有有效授权无需重复确认。
- 获得 push 授权后默认使用 SSH。优先使用仓库已有的 SSH push 地址；若 `origin` 是可明确转换的 HTTPS 地址，则使用等价 SSH 地址执行本次 push，不修改远端配置。SSH 不可用或地址无法可靠转换时如实报告并停止，不静默改用需要交互凭据的 HTTPS。
